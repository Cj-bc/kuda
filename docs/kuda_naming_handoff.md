# Kuda — 命名・世界観ハンドオフ

**宛先:** 設計・作業手順書を担当する Claude  
**目的:** 既存の `pcwatch`（仮称）について、プロジェクト名と今後の CLI・設定・内部概念の命名を検討する際の判断材料を共有する。  
**位置づけ:** 命名方針の共有。既存設計の変更指示ではない。

## 1. プロジェクトの概要

PC の状態を定期的・機械的に観測し、通常時の状態（ベースライン）と比較して異常や変化を検出する。異常時には LLM に調査・原因分析を依頼する。

例: 5 分ごとにネットワーク疎通を確認し、ping の遅延悪化・到達不能・traceroute の経路変化などを検知した際に、LLM に詳細調査を引き継ぐ。

**重要:** 通常時の観測と一次判定は、必ずしも LLM に依存しない。LLM は追加調査・解釈の段階で呼び出される。ここに書いていない機能・構成は既存の設計資料を正とする。

## 2. 名前の方向性

- **第一候補のプロジェクト名: `Kuda`**（管狐／くだぎつね、*kudagitsune* に由来）
- 従来の作業名: `pcwatch`
- CLI 名の候補: `kuda`。実行ファイル、デーモン名、設定ファイル名などは既存の設計と衝突状況を確認してから確定する。
- 表記: プロジェクト・製品名は **Kuda**、CLI やパッケージの識別子には **`kuda`** を基本候補とする。

これは単なる狐モチーフではなく、**使役される小さな存在が、見えないところで働き、異変を察知して主人に知らせる**という比喩を意図している。

## 3. 管狐を選ぶ理由と設計思想

伝承は地域や資料により異なるため、以下はモチーフとして採用した解釈であり、すべての伝承に共通する史実・設定だとは扱わない。

| 管狐のモチーフ | 本アプリでの対応 |
|---|---|
| 主人に使役される | Manifest や設定で観測対象・周期・動作を宣言する |
| 小さく、目立たず働く | バックグラウンドで継続的にテレメトリを取得する |
| 占い・予言・見通しを得る | 異常の兆候を捉え、LLM による原因推定・分析につなぐ |
| 管に入れて管理する | ツールの実行範囲、サンドボックス、権限、資源上限を明示的に制約する |
| 管理を怠ると増殖して厄介になる | 無制限の再試行、再帰的なエージェント実行、プロンプト・ツール権限の拡大、コスト増大を戒める |

**中心的なメッセージ:** Kuda は有能な使い魔だが、無制限の自由を与えるべきではない。特に LLM に与えるプロンプト、ツール権限、実行回数、タイムアウト、予算、追加調査の深さなどは明示的に管理する。

「管」は安全な境界の比喩として使える。ただし**名前だけで実際のサンドボックスや安全性が保証されるわけではない**。安全要件は別途、具体的に設計・検証すること。

## 4. CLI・内部用語の命名への反映

**基本方針:** 公開インターフェースの第一優先は、予測可能性・わかりやすさ・既存 CLI の慣習。民俗由来の語は、意味が直感的に伝わる場面か、ドキュメントで短く説明できる場面に限定する。既存の設計・作業手順に機械的に以下の名前を適用しないこと。

### 推奨する素直な CLI 例（すべて候補）

```sh
kuda init       # 設定の初期化
kuda status     # 稼働状態を確認
kuda check      # 観測・判定を手動実行
kuda logs       # 記録を閲覧
kuda diagnose   # 詳細調査（LLM を含む可能性）
```

これは**コマンドの仕様や実装を確定する一覧ではない**。実装済みの機能や操作モデルに合わせて採否を判断すること。たとえば `check` が取得のみか、検知まで含むか、`diagnose` が明示的起動を許すかは既存設計次第。

### 世界観に由来する任意の用語候補

| 用語 | 意味の候補 | 判断上の注意 |
|---|---|---|
| `manifest` | 主人が与える宣言的な指示 | 既存の一般的な技術用語として優先的に維持したい |
| `familiar` | 観測を担う使い魔／ワーカー | 技術的な責務の分割が明確な場合のみ |
| `tube` | 権限・実行範囲を制限する境界 | 伝承上の「管」の比喩。`sandbox` や `permissions` の方が明確ならそちらを採用 |
| `omen` | 異常の兆候・検知イベント | `anomaly` / `alert` と混同しないか確認 |
| `divination` | LLM による追加の分析・推定 | `diagnosis` / `analysis` の方が利用者に明確なら採用しない |
| `binding` | 使い魔への制約 | 権限・予算・実行上限を曖昧にまとめすぎないこと |

マスコットや README で世界観を積極的に出すのは歓迎。一方、CLI ヘルプ、設定スキーマ、エラーメッセージは説明性を優先する。

## 5. Claude にお願いしたいこと

1. 今後の設計・作業手順書では、特段の不都合がなければプロジェクト名を **Kuda** として扱い、`pcwatch` は旧仮称として認識する。
2. 新しい CLI サブコマンド、設定キー、モジュール名、ログの名称を提案する際に、このモチーフを参考にする。ただし**伝承に合わせるためだけの仕様変更はしない**。
3. 命名が競合したら、**役割が正確に伝わる既存の技術用語 > 一貫性 > 世界観の面白さ**の順で判断する。
4. LLM の呼び出しと権限の境界を設計する際には、「管狐を管の外へ無制限に出さない」という戒めを設計レビューの観点として意識する。実際の安全策は、許可ツール・入力の信頼境界・実行上限・リトライ制御・監査可能性など、検証可能な要件として表現する。
5. コマンド名、パッケージ名、ドメイン名などを最終確定する前に、既存ソフトウェアとの重複、公開先レジストリ、商標上の懸念を確認する（未調査）。
6. 既存の作業手順書に影響する命名変更があれば、**変更案・理由・互換性への影響**を明記する。既存 API やファイルを黙ってリネームしない。
